# Dev Harness — конвейер работы агента

Этот скилл задаёт «харнесс»: фиксированный порядок работы над любой задачей разработки.
Каждая задача проходит один и тот же конвейер с контрольными точками, поэтому результат
предсказуем и проверяем. Фазы нельзя пропускать, но объём работы внутри фазы масштабируется
от размера задачи.

## Когда применять

Применять ко всем задачам, меняющим код, тесты, конфигурацию, миграции или документацию:
новая фича, багфикс, рефакторинг, правка схемы БД, правка CI.

Не применять к запросам без изменения кода («объясни», «посмотри», «что тут не так») —
на них достаточно обычного ответа с разбором.

## Конвейер

### Фаза 0 — Приём задачи

1. Переформулируй задачу своими словами в 1–3 предложениях: «Делаю X, чтобы Y».
2. Определи критерий готовности: по какому признаку пользователь поймёт, что задача решена.
3. Если задача допускает существенно разные трактовки — задай ОДИН уточняющий вопрос
   с вариантами («делаю А или Б?»), а не серию вопросов. Если трактовка очевидна —
   не спрашивай, действуй.

### Фаза 1 — Разведка

1. Прочитай релевантный код ДО изменений. Не предполагай структуру проекта — проверяй
   инструментами (поиск, чтение файлов).
2. Найди похожую реализацию в проекте и следуй её паттерну: структура пакетов, обработка
   ошибок, логирование, стиль тестов.
3. Проверь, есть ли тесты на затрагиваемый код — их, скорее всего, придётся обновить.
4. Если в проекте есть CONVENTIONS.md, README или Makefile с правилами — прочитай их
   до начала работы.

### Фаза 2 — План

1. Задача в один файл и до ~30 строк — план не нужен, переходи сразу к реализации.
2. Задача больше — составь план: список шагов с файлами, которые будут созданы/изменены,
   и порядком выполнения.
3. Покажи план пользователю и ЖДИ подтверждения, если затрагивается хотя бы одно из:
   архитектура проекта, публичный API, схема БД или миграции, новая зависимость.
   Во всех остальных случаях действуй без паузы.

### Фаза 3 — Реализация

1. Минимальный дифф: меняй только то, что относится к задаче.
2. Работай шагами: один логический шаг → проверка (сборка/тесты затронутых пакетов) →
   следующий шаг. Не копи изменения «всё сразу».
3. Новую зависимость добавляй только при обоснованной необходимости и объясни в отчёте,
   зачем она.
4. Заметил баг, не связанный с задачей — не чини его. Запиши и упомяни в отчёте.
5. Не оставляй закомментированный код, мёртвый код и пустые заглушки.

### Фаза 4 — Верификация (обязательная)

Прогони по возрастанию и добейся зелёного статуса:

```
go build ./...
go vet ./...
go test ./...
```

- Сначала тесты затронутых пакетов, затем весь проект. Для конкурентного кода —
  `go test -race ./...`.
- Если в проекте появился Makefile/линтер — используй его цели вместо сырых команд.
- Красный тест из-за твоих изменений — чини. Красный до твоих изменений — не чини,
  укажи в отчёте.
- НИКОГДА не утверждай «тесты прошли», если не видел вывод команды в этом запуске.

### Фаза 5 — Самопроверка

Прочитай `CHECKLIST.md` (лежит рядом с этим файлом) и пройдись по нему применительно
к своему диффу. Каждый проваленный пункт либо исправь, либо обоснуй в отчёте, почему
исправить нельзя.

### Фаза 6 — Отчёт

Ответ пользователю по структуре:

- **Что сделано** — кратко, списком.
- **Файлы** — что создано и изменено.
- **Проверка** — какие команды запущены и с каким результатом.
- **Замечания** — риски, найденные сторонние баги, что осталось сделать.

## Инварианты (действуют во всех фазах)

- Не делай git commit, ветки, push и merge без явной просьбы пользователя.
- Не переписывай и не переименовывай то, что не просили, даже если «так лучше».
- Секреты — только через env/конфиг, никогда в коде и тестах.
- Не выдумывай факты о коде: «проверил» = реально запускал команду; предположение —
  явно помечай как предположение.
- Если в середине работы понял, что план неверен — остановись, скажи об этом и предложи
  новый план. Не меняй направление молча.
- Задача не считается завершённой без Фазы 4. Если верификацию запустить невозможно
  (нет окружения, нет тестов) — явно скажи об этом в отчёте и что нужно, чтобы проверить.
